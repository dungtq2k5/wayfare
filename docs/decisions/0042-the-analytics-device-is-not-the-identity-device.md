# 0042 — The analytics device id is not the identity device id

**Status:** Accepted · **Date:** 2026-09-14 · **Supersedes:** — · **Superseded by:** —

## Context

The identity service already has a stable anonymous device id, and every analytics event comes from a device. Reusing that id is the easy path.

It would also make the privacy promise false. The identity device id is stable, can be claimed by an account, and appears in favourites and orders. Any analytics row carrying it is one join away from a named person's movement history — the thing product-overview §10 says the system must never be able to reconstruct.

## Decision

Analytics uses a **separate `analytics_device_id`**, generated by the client, sent only to the `analytics` service, **rotated every 30 days**, and discarded when consent is withdrawn. No table in any service maps one id to the other, and no event carries both.

Location reaches analytics only as a client-snapped geohash cell, and heatmap tables store HyperLogLog device *counts*, never ids.

## Consequences

- The consent and anonymisation claims are enforced by the schema rather than by policy.
- Per-device longitudinal analysis beyond 30 days is impossible, and "active devices" figures are upper-bound estimates. Accepted and labelled in dashboards.
- A future feature that wants to join analytics to accounts must supersede this ADR explicitly, which is the point.
