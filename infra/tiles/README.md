# infra/tiles — map packs

`pnpm tiles:build --area <code>` builds an area's self-hosted map pack ([architecture §6](../../docs/architecture-and-tech-stack.md), [ADR 0023](../../docs/decisions/0023-self-hosted-pmtiles-no-tile-vendor.md)) and uploads it to the media bucket under `maps/<areaCode>/<buildId>/`, where `buildId` is the first 16 hex characters of the archive's SHA-256. It prints the `POST /admin/map-packs` body, also written to `.cache/build/<code>/register.json`. An admin then registers the pack, which re-hashes every object, and publishes it.

## What it does

1. **The area's box.** For a seeded area it reads `services/catalog/prisma/seed/pilot-*/area.json`. An area an admin created takes `--bbox <w,s,e,n> --area-id <uuid>`. The box is widened by 500 m on every side.
2. **The archive.** `pmtiles extract` cuts the area from the pinned Protomaps daily planet build, from zoom `MIN_ZOOM` to the build's maximum (z15). It fetches only the byte ranges it needs, so it takes seconds and little memory; no service needs to be running.
3. **The glyphs.** For each font stack the style uses, it takes the five ranges in `MAP_PACK_GLYPH_RANGES` from the pinned `protomaps/basemaps-assets` commit. U+1E00–1EFF is among them, which Vietnamese street names need; the build fails without it.
4. **The sprites.** It takes the pinned flavour's sprites (`sprites/v4/<flavor>`, 1× and 2×) from the same commit.
5. **The style.** `upload.mjs` generates it from the pinned `@protomaps/basemaps` package, labels in `BASEMAPS_LANG`, with **absolute** URLs under `GCS_PUBLIC_BASE_URL`: `pmtiles://…/map.pmtiles`, the glyphs and the sprite.
   - The web client registers the `pmtiles://` protocol handler and uses the style as it is.
   - The mobile client replaces the `GCS_PUBLIC_BASE_URL` prefix with the pack's local directory at activation.
6. **The budget and the upload.** Over `MAX_MAP_PACK_BYTES` (60 MB, the archive and its assets together) the build stops before uploading. The objects are immutable: `Cache-Control: public, max-age=31536000, immutable`. Storage settings are catalog's own, read from `services/catalog/.env`: `GCS_BUCKET_MEDIA`, `GCS_API_ENDPOINT` (locally, fake-gcs) and `GOOGLE_APPLICATION_CREDENTIALS`.

`--no-upload` stops after step 4, leaving the files in `.cache/build/<code>/`.

Locally, run `pnpm --filter @wayfare/catalog storage:setup` once so the media bucket exists with its CORS rules; the second rule lets a browser make range reads.

## Moving a pin forward

Every input is pinned in `versions.env`. Protomaps removes old daily builds after a while; when `PROTOMAPS_BUILD_URL` answers `404`, pick a newer date from <https://maps.protomaps.com/builds/>. Check its maximum zoom with `.cache/pmtiles-<version>/pmtiles show <url>` and set `MAX_ZOOM` to match. Then rebuild, register and publish. The previous pack is retired, and its objects are deleted 30 days later (`map-packs-prune`).

When `BASEMAPS_VERSION` moves, move `BASEMAPS_ASSETS_COMMIT` with it: the style names the font stacks and sprites that commit provides.

## After a lost bucket

The emulator keeps its objects in a named volume, so `docker compose down` and `up` keep them. `docker compose down -v` does not — and then narration's `audio_assets` and catalog's rows still name files that are gone. To come back:

1. `pnpm --filter @wayfare/catalog storage:setup` — the bucket and its CORS rules.
2. `pnpm tiles:build --area <code>` for every registered pack. The build is deterministic, so the same bytes land on the same `maps/<areaCode>/<buildId>/` paths and the existing rows stay valid; nothing is re-registered. Register a new pack only if a pin in `versions.env` has moved since.
3. `pnpm recover:narration` — retries the jobs that failed while the bucket was gone, and regenerates the Places whose audio objects went with it.

Photos are not recoverable: the seed commits none, so whatever a walk uploaded is gone for good. Delete the Places that hold them, or replace their photos through the console.
